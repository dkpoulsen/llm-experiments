- [[fullyshardeddataparallel-pytorch-213-documentation]] — FullyShardedDataParallel — PyTorch 2.13 documentation — PyTorch 2.13 FullyShardedDataParallel API documentation (torch.distributed.fsdp) — the primary reference for exactly what FSDP moves over the wire and how it treats frozen parameters. Sharding strategies: FULL_SHARD all-gathers parameters before the forward, reshards after it, all-gathers again before backward, reshards after backward, and reduce-scatters gradients after backward, with optimizer states updated locally per rank; SHARD_GRAD_OP unshards before forward but does not reshard until after backward (so parameters stay gathered between passes); NO_SHARD is DDP-equivalent and all-reduces gradients; HYBRID_SHARD does FULL_SHARD within a node and replicates across nodes, cutting communication volume because the expensive all-gathers and reduce-scatters stay intra-node. Memory/overlap knobs: backward_prefetch=BACKWARD_PRE holds current params, next params and current gradients at peak (most overlap, most memory) while BACKWARD_POST frees current params before allocating the next set; limit_all_gathers (default True) is a rate limiter that caps GPU memory to two consecutive FSDP instances' worth of gathered parameters. Frozen-parameter constraint, directly relevant to a frozen-Engram plan: with use_orig_params=False each FSDP instance must manage parameters that are all frozen or all non-frozen; with use_orig_params=True FSDP supports mixing frozen and non-frozen parameters but recommends against it because of higher-than-expected gradient memory. Also: FSDP cannot run the forward of a submodule contained in an FSDP instance (its params are sharded but no all-gather happens), and mixed precision can be disabled per module at the cost of separate all-gathers/reduce-scatters. Relevance: this is the authoritative source for the claim that FSDP's per-layer all-gather/reduce-scatter pattern is what makes it expensive on a slow fabric, and it shows the frozen-table plan needs its own all-frozen FSDP unit rather than a mixed unit. `review`

- [[zipccl-efficient-lossless-data-compression-of]] — ZipCCL: Efficient Lossless Data Compression of — ZipCCL (Lin, Pan, Fan, Shi, Chu; arXiv 2604.27844) is a lossless compression layer for NCCL collectives in LLM training. Core observation: LLM training tensors (activations, gradients, parameters) are near-Gaussian, so BF16 exponents are highly concentrated - the top-7 most frequent exponents cover >97% of the data. ZipCCL encodes each BF16 exponent in 3 bits (7 codes plus a zero-point escape flag) instead of 8, leaving sign/mantissa untouched, for a theoretical compression ratio up to 11 bits from 16 (~1.45x). It adds GPU-optimised compress/decompress kernels with communication-aware data layout and an adaptive switcher driven by a cost model over measured bandwidth, latency and compression ratio.

Evaluation: 64-GPU cluster of 8x RTX A6000 per node over a 200 Gb/s network, integrated into Megatron-LM (MoE all-to-all) and TorchTitan (FSDP all-gather/reduce-scatter), plus a 16xH800 400 Gb/s cluster. Communication speedups over NCCL: 1.25x on DeepSeek-V3 all-to-all, 1.24x on Qwen3-MoE, 1.35x on Llama3-8B all-gather; averaged across message sizes 1.36x for all-to-all and 1.31x for all-gather. End-to-end training speedups: 1.16x (DeepSeek-V3), 1.16x (Qwen3-MoE), 1.18x (Llama3-8B); on the 16xH800 cluster 1.13x for both Qwen3-MoE and Llama3-8B.

Two findings are load-bearing for this box. First, the benefit is bandwidth-saturation dependent: "When the data volume is small, bandwidth cannot be fully utilized, and our ZipCCL shows very close performance to NCCL. However, as the data volume increases ... and bandwidth is better saturated, the improvement ... becomes significant." On a ~1 GB/s fabric the saturation point arrives at far smaller tensors, so 1.3x is a floor rather than a ceiling. Second, Reduce-Scatter was NOT worth compressing on their platform ("the original Reduce-Scatter implementation was found to be faster"), so a DDP/FSDP gradient path does not automatically inherit the gain - all-gather did, reduce-scatter did not.

Also notable: ZipCCL beats DietGPU (Meta's GPU lossless compressor), where DietGPU-compressed all-gather was slower than plain NCCL all-gather while ZipCCL got 1.35x. The scheme is bit-exact, so unlike FP8/quantisation work it carries no convergence risk; the relevant risk on this box is compress/decompress kernel cost against 5 weak GPUs. `review`

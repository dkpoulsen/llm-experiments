- [[communication-efficient-distributed-training]] — Communication-Efficient Distributed Training — Munim & Ramamoorthy (arXiv 2609.23898v2, cs.IT, 26 Sep 2026) propose CERAR, a Communication-Efficient Ring All-Reduce protocol that trades exactness for bandwidth: each worker splits its gradient into c chunks, linearly encodes them (Vandermonde, or a condition-number-constrained construction), and runs L = c + N - 2 rounds over an N-worker ring, giving normalized per-worker communication 1 + (N-2)/c instead of ring all-reduce's 2(N-1)/N, at the cost of a bounded approximation error (~1.6-2.9% relative l2 gradient error in their training runs). The Vandermonde route is asymptotically exact as c grows but ill-conditioned; they give an alternate scheme with error O(eps) and condition number O(eps^-r*), r* = ceil(c/N) - 1, plus a constrained optimization for practical designs.

The headline empirical result lands on the fabric that matters for this box: on a single node of 8x A100 PCIe (interconnect characterised as 31.5 GB/s), CERAR cuts raw all-reduce time by 46.0-47.1% versus NCCL - a 1B-entry FP32 tensor goes from 17,954.4 ms (NCCL) to 9,558.6 ms (CERAR); 500M entries 8,611.2 -> 4,651.0 ms; 100M 1,775.9 -> 940.1 ms. On 4x H200 SXM over NVLink (>=300 GB/s) the same scheme is 33.2-33.9% SLOWER than NCCL (24B entries: 392.049 ms NCCL vs 522.366 ms CERAR), so the win is explicitly a low-bandwidth-fabric phenomenon, not a general one.

End-to-end: Pythia-1.4B on 4x A100 PCIe 40GB for 1,800 steps (~117.96M tokens) takes 3.79 h with NCCL vs 3.14 h with CERAR (-17.3%, ~39 min saved), throughput 8,644 -> 10,451 tok/s, final validation loss 1.4218 vs 1.4213 (essentially identical), peak memory 36.2 vs 38.6 GB. On 4x A100 SXM 80GB over NVLink CERAR is 3.65% slower (4.745 h vs 4.578 h).

Caveats the drafter must carry: (i) the authors call their implementation a proof of concept, not optimised to NCCL's level (NCCL uses multiple channels and compute/comm overlap); (ii) encoding/decoding compute is real and grows with c, so on a box whose GPUs are also weak the arithmetic overhead is not free; (iii) the tested PCIe fabric is 31.5 GB/s, roughly 30x the ~0.75 GiB/s NCCL all-reduce measured on the CMP 170HX box, so the communication-bound regime is far deeper here - the direction of the effect should hold, the magnitude is not transferable; (iv) the approximation error is ~2-3% relative on gradients, a training-quality risk the paper argues is benign at 1.4B scale only. `review`

- [[demystifying-nccl-an-in-depth-analysis-of-gpu]] — Demystifying NCCL: An In-depth Analysis of GPU — Demystifying NCCL (Hu, Shen et al., ETH Zurich + NVIDIA + Broadcom, arXiv 2507.04786, HOTI 2025): the primary reference for what NCCL actually does on a given fabric, and the mechanism behind the box's measured ~0.75 GiB/s all-reduce. Three protocol variants: Simple (near-peak bandwidth for large messages, ~6 us per-hop latency, memory fences), LL (4 B data + 4 B flag per 8-byte atomic, ~1 us per-hop, but only 25-50% of peak bandwidth because LL FORCES the intermediate buffer into host memory so the CPU can poll the flag, which precludes GPUDirect RDMA), and LL128 (120 B data + 8 B flag, ~95% of peak, ~2 us per-hop, but requires atomic 128-byte writes that are not split or reordered — NCCL disables LL128 on PCIe where that guarantee is absent). Intra-node transports are P2P (p2p.cc, GPUDirect P2P over NVLink or PCIe), SHM (shm.cc, host-staged), and NVLS; NCCL falls back to SHM not only when P2P is unavailable but also when P2P is suboptimal, e.g. inter-socket PCIe P2P. Algorithmically, Ring AllReduce executes 2k-1 steps per loop iteration and is NON-pipelined (each GPU must finish every task in one iteration before starting the next), so it is latency-bound on host-staged links; Tree AllReduce is pipelined but builds its branching structure only across nodes and links the GPUs inside a node in a simple chain, so on a single-node 5-GPU box the tree degenerates to a chain and buys nothing over ring. `review`
- [[efficient-expert-parallel-communication]] — Efficient Expert-Parallel Communication — ThunderEP (Lee et al., Seoul National University, arXiv 2609.40093): an EP communication design for MoE inference on PCIe consumer GPUs with no P2P. - [[efficient-multi-path-nvlinkpcie-aware-ucx-based-collective-communication-for-dee]] — Efficient Multi-Path NVLink/PCIe-Aware UCX based Collective Communication for Deep Learning — Temucin, Sojoodi, Alizadeh & Afsahi (HOTI 2021, Queen's University) show that a single NVLink/PCIe path badly under-utilises intra-node GPU-GPU bandwidth, and fix it with a multi-path copy that stripes messages across multiple NVLink channels, memory regions and GPU streams. On UCX this yields 1.69x higher bandwidth (72 -> ~122 GB/s) and 1.84x on Open MPI + UCX (up to 134 GB/s), on a 4xV100 POWER9 node with three intra-socket NVLinks.

They then build a 3-stage hierarchical, pipelined MPI_Allreduce: multi-path NVLink for intra-socket stages 1 and 3, and PCIe / X-Bus channels for the inter-socket stage 2, chosen per message size to minimise interference (PCIe Gen4 and X-Bus are both ~32 GB/s, so the X-Bus is the bottleneck on the NVLink-X-Bus-NVLink path). It outperforms NCCL for all messages >8 MB.

At the application layer with Horovod+TensorFlow: VGG16 gets up to 2.98x/3.42x/3.22x/1.23x/3.24x over those five libraries, ResNet50 1.50x/1.57x/1.22x/1.24x/1.23x.

Why it matters here: it establishes that NCCL is not a hard ceiling on a PCIe/NVLink intra-node fabric - a hierarchical collective that uses ALL available paths (including the host X-bus staging path a no-P2P box is forced onto anyway) can beat it by ~1.25x at >=8 MB. The mechanism is dated (2021, V100, NCCL 2.5.6) but the structural insight - one path at a time wastes bandwidth - is exactly the situation on a 5-GPU box with no P2P, where every collective round-trips through host RAM. `review`

- [[environment-variables-nccl-2323-documentation]] — Environment Variables — NCCL 2.32.3 documentation — NVIDIA's official NCCL 2.32.3 environment-variable reference - the primary source behind the tuning claims in the ClusterBid blog. Load-bearing entries for a no-P2P PCIe box:

NCCL_P2P_DISABLE disables the peer-to-peer transport ("CUDA direct access between GPUs, using NVLink or PCI"). NCCL_P2P_LEVEL sets the maximum topological distance at which P2P is used, with named levels LOC (never), NVL (NVLink), PIX (same PCI switch), PXB (through PCI switches, possibly multiple hops), PHB (same NUMA node, traffic through the CPU) and SYS (across NUMA nodes, potentially crossing QPI/UPI). Integer legacy values 0-4 map to LOC/PIX/PXB/PHB/SYS; NVL has no legacy integer.

NCCL_SHM_DISABLE documents the fallback path that matters most here: "SHM is used between devices when peer-to-peer cannot happen, therefore, host memory is used." That is the primary confirmation that a no-P2P box stages every collective through host RAM, and it names the knob (NCCL_SHM_DISABLE) that would force the network path instead.

NCCL_ALGO accepts Ring, Tree, Collnet, CollnetChain, CollnetDirect, NVLS, NVLSTree and PAT (2.23+), with per-function selection syntax since 2.24 and caret-prefixed exclusion lists. Default is unset, i.e. NCCL picks automatically from node topology and architecture. NCCL_PROTO accepts LL, LL128 and Simple; the docs warn users are "discouraged from setting this variable" and that "enabling LL128 on platforms that don't support it can lead to data corruption" - a direct caution against blindly copying tuning recipes.

Other relevant knobs: NCCL_BUFFSIZE, NCCL_NTHREADS, NCCL_MIN_NCHANNELS / NCCL_MAX_NCHANNELS (channel count trades CUDA blocks for bandwidth), NCCL_NVB_DISABLE (intra-node NVLink via an intermediate GPU), NCCL_PXN_DISABLE, NCCL_NET_GDR_LEVEL, and NCCL_IB_* for RDMA fabrics. Notably the docs do not support the blog's claim that NCCL_ALGO=Ring with NCCL_PROTO=LL is a recommended setting for >256-GPU clusters; that is vendor-blog folklore, not documented guidance. `review`
- [[evaluating-modern-gpu-interconnect-pcie]] — Evaluating Modern GPU Interconnect: PCIe, — Li, Song, Chen, Li, Liu, Tallent & Barker (PNNL; arXiv 1903.04611, IEEE TPDS) is the canonical primary evaluation of modern GPU interconnects - PCIe, NVLink-V1, NVLink-V2, NV-SLI, NVSwitch and GPUDirect-RDMA - across six platforms: P100-DGX-1, V100-DGX-1, DGX-2, OLCF SummitDev, Summit, and a 2x Turing RTX-2080 SLI system. They measure raw startup latency, sustainable uni/bidirectional bandwidth, topology, routing and NUMA effects under both P2P and collective (NCCL) patterns.

Four new NUMA effects are identified: three triggered by NVLink topology/connectivity/routing, and one by a PCIe chipset design issue they label "anti-locality" - nearby access presenting LOWER performance than remote access, observed only for bandwidth (not latency) and appearing for messages >64 KB. PCIe latency is essentially uniform across pairs (same through one PCIe switch, across a local CPU socket, or across the QPI bridge), i.e. no NUMA effect in PCIe latency; NVLink latency is ~9 us direct and rises ~2x (P100) / ~3x (V100) when routing is required. NV-SLI: local 5 us, NV-SLI 8 us, PCIe 13 us. NVSwitch gives 50 GB/s bidirectional per link, 300 GB/s via a single NVSwitch hop, and 2.4 TB/s baseboard-to-baseboard bisection.

Message-size saturation points differ by an order of magnitude: NCCL collective bandwidth saturates at ~16 MB on PCIe but ~256 MB on NVLink (8 GPUs); on a 2-GPU SLI system both PCIe and NV-SLI saturate at ~1 MB.

THE finding for this run: "the NUMA effects appear quite significant with 5 GPUs, implying that there may be a congestion when forming a NCCL ring among 5 GPUs. One should avoid adopting 5 GPUs in their application setup." The box under assessment has exactly 5 GPUs, so this is a direct, primary-sourced warning that a 5-rank NCCL ring is a pathological configuration on PCIe.

Their discussion adds two structural cautions: NVLink's advantage is bandwidth, not latency, over PCIe; and a faster interconnect alone "can hardly become significant enough to lift the entire application's speedup" unless the CPU-centric master-slave programming model is replaced or communication control moves to the GPU (e.g. NVSHMEM). NVLink also introduces its own overheads (enable/disable peer access, routing, NCCL initialization). `review`
- [[fire-flyer-ai-hpc-a-cost-effective]] — Fire-Flyer AI-HPC: A Cost-Effective — Fire-Flyer AI-HPC (DeepSeek-AI, arXiv 2408.14158, SC24): the production-cluster counterexample that matters most for this run — a 10,000-GPU cluster built entirely from PCIe A100s (no NVLink in the original design), reaching performance approximating DGX-A100 at half the cost and 40% less energy. Its contribution HFReduce is a CPU-based all-reduce designed for exactly this fabric: intra-node reduce first (async D2H copy of gradients to pinned host memory, reduction with CPU vector instructions), then inter-node all-reduce over RDMA using a double-binary-tree, then H2D back to the GPUs (GDRCopy lets one host read feed four GPUs on the same NUMA node, cutting host reads 3x). The bandwidth argument is the load-bearing part: NCCL's ring topology sends each unit of data through 2n-1 transmissions, consuming (2n-1)/n units of PCIe bidirectional bandwidth — 1.8 units at n=5 — whereas HFReduce consumes exactly 1 unit (one D2H plus one H2D). HFReduce also uses the GPU copy engine rather than SM kernels, so it does not steal compute. Relevance: it establishes that a PCIe-only fabric is a legitimate production training substrate, and that replacing NCCL's ring all-reduce with a host-reduction scheme is worth roughly 2-4x on the exact bottleneck this box has. `review`
- [[github-mcrltccl-thunder-research-groups-collective-communication-library-github]] — GitHub - mcrl/tccl: Thunder Research Group's Collective Communication Library · GitHub — TCCL (Thunder Research Group, SNU; ASPLOS 2024; github.com/mcrl/tccl): a fork of NCCL for 'PCIe-dependent systems' — clusters where GPUs must communicate through the CPU's PCIe host bridge and possibly NUMA interconnects, with no NVLink and no external PCIe switches. Its premise is the key claim for this run: existing collective libraries do NOT achieve the performance their analytical models predict on PCIe-dependent systems, for two reasons that only appear when traffic goes through the CPU — transfers slow down when multiple transfers traverse the CPU in a particular pattern because of NUMA architecture, and bounce buffers are poorly placed when GPUs communicate via CPU memory. TCCL's pathfinder profiles each candidate communication path and merges single-node paths into multi-node paths (brute force is exponential in GPU count), and the runtime is a drop-in libnccl.so replacement selected via NCCL_ALGO=TCCL plus TCCL_XML_FILE. - [[quantifying-interconnect-energy-efficiency-on-perlmutter-pjbit-measurements-of-n]] — Quantifying Interconnect Energy Efficiency on Perlmutter: pJ/bit Measurements of NVLink, PCIe, Slingshot NICs, and Rosetta Switches — Zhao, Williams, Antepara, Oliker, Austin & Wright (LBNL, eScholarship qt67z0d2wn, 2026-04-28) measure dynamic energy per bit for the interconnects on Perlmutter (HPE Cray EX, A100 GPUs, NERSC) with a software-centric microbenchmark methodology that correlates controlled stress on one component with job- and rack-level power telemetry, separating dynamic energy from constant-power overhead.

Headline pJ/bit figures: NVLink 70.9 +/- 1.0 pJ/bit, PCIe (host<->GPU) 167.9 +/- 10.5 pJ/bit, NIC+PCIe (host<->Cassini NIC) 4.1 +/- 3.2 pJ/bit, and the GPU DMA engine ~48 pJ/bit at 93.55 GB/s. Moving a bit over PCIe into/out of the GPU costs ~2.4x what it costs over NVLink - the quantitative version of "PCIe is the expensive path".

The mechanism they identify is the "Active Tax": waking an A100's command processor, memory fabric and PCIe PHY from deep idle to P0 costs roughly 50 W of uncore power. Their H2D run shows GPU0 drawing 55.00 W at 24.94 GB/s (of a 32 GB/s PCIe Gen4 peak), and D2H 55.50 W at 24.53 GB/s - the transfer is dominated by the wake-up cost, not the payload. The host->NIC path bypasses the GPU entirely and therefore avoids the tax, which is why NIC+PCIe comes out at 4.1 pJ/bit.

Relevance to the CMP box: every collective on a no-P2P fabric stages through host RAM, so each GPU pays the PCIe path energy (167.9 pJ/bit) AND the ~50 W uncore wake-up tax on every transfer. On a card capped at 250 W, a 50 W uncore tax is 20% of the power budget spent moving bits rather than doing math - a real efficiency argument for large-batch, low-frequency communication (DDP with big global batches and gradient accumulation) and against per-layer all-to-alls. Caveat: measured on A100/PCIe Gen4 with full telemetry; the CMP 170HX has weaker telemetry and a Gen2 x4 link, so absolute pJ/bit will differ, but the direction (PCIe >> NVLink, plus a fixed wake-up tax) is architectural. `review`
- [[variopath-workload-aware-all-to-all-communication-for-pcie-gpu-clusters]] — VarioPath: Workload-Aware All-to-All Communication for PCIe GPU Clusters — VarioPath (Fei et al., USTC + Tsinghua, arXiv 2609.34340): workload-aware AlltoAllv scheduling for PCIe GPU clusters — the primitive that EP dispatch/combine and sequence parallelism are built from. It documents why PCIe all-to-all is hard: no dedicated scale-up fabric means intra-node GPU traffic and NIC traffic share the same PCIe hierarchy, so concurrent transfers contend on bottleneck links; demand is skewed (top-k routing) and changes every layer (sub-millisecond per layer), defeating static schedules. VarioPath splits an offline topology-aware analyzer (records contention-free transfer patterns as channels, exploits topology symmetry) from an online demand-aware scheduler. On four platforms up to 256 GPUs it averages 5.88x over FAST and 1.72x over DeepEP (1.55-2.00x geomean over DeepEP on random-demand AlltoAllv, 3.73-10.61x over NCCL), reaching 30.91 GB/s algorithmic bandwidth at 256 GPUs vs 28.11 (DeepEP) and 18.85 (NCCL).

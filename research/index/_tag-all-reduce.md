- [[communication-efficient-distributed-training]] — Communication-Efficient Distributed Training — Munim & Ramamoorthy (arXiv 2609.23898v2, cs.IT, 26 Sep 2026) propose CERAR, a Communication-Efficient Ring All-Reduce protocol that trades exactness for bandwidth: each worker splits its gradient into c chunks, linearly encodes them (Vandermonde, or a condition-number-constrained construction), and runs L = c + N - 2 rounds over an N-worker ring, giving normalized per-worker communication 1 + (N-2)/c instead of ring all-reduce's 2(N-1)/N, at the cost of a bounded approximation error (~1.6-2.9% relative l2 gradient error in their training runs). The Vandermonde route is asymptotically exact as c grows but ill-conditioned; they give an alternate scheme with error O(eps) and condition number O(eps^-r*), r* = ceil(c/N) - 1, plus a constrained optimization for practical designs.

The headline empirical result lands on the fabric that matters for this box: on a single node of 8x A100 PCIe (interconnect characterised as 31.5 GB/s), CERAR cuts raw all-reduce time by 46.0-47.1% versus NCCL - a 1B-entry FP32 tensor goes from 17,954.4 ms (NCCL) to 9,558.6 ms (CERAR); 500M entries 8,611.2 -> 4,651.0 ms; 100M 1,775.9 -> 940.1 ms. On 4x H200 SXM over NVLink (>=300 GB/s) the same scheme is 33.2-33.9% SLOWER than NCCL (24B entries: 392.049 ms NCCL vs 522.366 ms CERAR), so the win is explicitly a low-bandwidth-fabric phenomenon, not a general one.

End-to-end: Pythia-1.4B on 4x A100 PCIe 40GB for 1,800 steps (~117.96M tokens) takes 3.79 h with NCCL vs 3.14 h with CERAR (-17.3%, ~39 min saved), throughput 8,644 -> 10,451 tok/s, final validation loss 1.4218 vs 1.4213 (essentially identical), peak memory 36.2 vs 38.6 GB. On 4x A100 SXM 80GB over NVLink CERAR is 3.65% slower (4.745 h vs 4.578 h).

Caveats the drafter must carry: (i) the authors call their implementation a proof of concept, not optimised to NCCL's level (NCCL uses multiple channels and compute/comm overlap); (ii) encoding/decoding compute is real and grows with c, so on a box whose GPUs are also weak the arithmetic overhead is not free; (iii) the tested PCIe fabric is 31.5 GB/s, roughly 30x the ~0.75 GiB/s NCCL all-reduce measured on the CMP 170HX box, so the communication-bound regime is far deeper here - the direction of the effect should hold, the magnitude is not transferable; (iv) the approximation error is ~2-3% relative on gradients, a training-quality risk the paper argues is benign at 1.4B scale only. `review`
- [[efficient-multi-path-nvlinkpcie-aware-ucx-based-collective-communication-for-dee]] — Efficient Multi-Path NVLink/PCIe-Aware UCX based Collective Communication for Deep Learning — Temucin, Sojoodi, Alizadeh & Afsahi (HOTI 2021, Queen's University) show that a single NVLink/PCIe path badly under-utilises intra-node GPU-GPU bandwidth, and fix it with a multi-path copy that stripes messages across multiple NVLink channels, memory regions and GPU streams. On UCX this yields 1.69x higher bandwidth (72 -> ~122 GB/s) and 1.84x on Open MPI + UCX (up to 134 GB/s), on a 4xV100 POWER9 node with three intra-socket NVLinks.

They then build a 3-stage hierarchical, pipelined MPI_Allreduce: multi-path NVLink for intra-socket stages 1 and 3, and PCIe / X-Bus channels for the inter-socket stage 2, chosen per message size to minimise interference (PCIe Gen4 and X-Bus are both ~32 GB/s, so the X-Bus is the bottleneck on the NVLink-X-Bus-NVLink path). For 512 KB-1 GB messages the hierarchical allreduce beats Spectrum MPI, Open MPI+UCX, Open MPI+HPC-X, MVAPICH2-GDR and NCCL by up to 12.25x, 15.63x, 3.72x, 1.48x and 1.38x respectively; at 64 MB specifically the speedups are 11.47x, 14.33x, 1.09x, 1.26x and 1.25x. It outperforms NCCL for all messages >8 MB.

At the application layer with Horovod+TensorFlow: VGG16 gets up to 2.98x/3.42x/3.22x/1.23x/3.24x over those five libraries, ResNet50 1.50x/1.57x/1.22x/1.24x/1.23x.

Why it matters here: it establishes that NCCL is not a hard ceiling on a PCIe/NVLink intra-node fabric - a hierarchical collective that uses ALL available paths (including the host X-bus staging path a no-P2P box is forced onto anyway) can beat it by ~1.25x at >=8 MB. The mechanism is dated (2021, V100, NCCL 2.5.6) but the structural insight - one path at a time wastes bandwidth - is exactly the situation on a 5-GPU box with no P2P, where every collective round-trips through host RAM. `review`

NCCL_P2P_LEVEL sets the maximum topological distance at which P2P is used, with named levels LOC (never), NVL (NVLink), PIX (same PCI switch), PXB (through PCI switches, possibly multiple hops), PHB (same NUMA node, traffic through the CPU) and SYS (across NUMA nodes, potentially crossing QPI/UPI). NCCL_SHM_DISABLE documents the fallback path that matters most here: "SHM is used between devices when peer-to-peer cannot happen, therefore, host memory is used." NCCL_ALGO accepts Ring, Tree, Collnet, CollnetChain, CollnetDirect, NVLS, NVLSTree and PAT (2.23+), with per-function selection syntax since 2.24 and caret-prefixed exclusion lists. NCCL_PROTO accepts LL, LL128 and Simple; the docs warn users are "discouraged from setting this variable" and that "enabling LL128 on platforms that don't support it can lead to data corruption" - a direct caution against blindly copying tuning recipes.

Other relevant knobs: NCCL_BUFFSIZE, NCCL_NTHREADS, NCCL_MIN_NCHANNELS / NCCL_MAX_NCHANNELS (channel count trades CUDA blocks for bandwidth), NCCL_NVB_DISABLE (intra-node NVLink via an intermediate GPU), NCCL_PXN_DISABLE, NCCL_NET_GDR_LEVEL, and NCCL_IB_* for RDMA fabrics. - [[zipccl-efficient-lossless-data-compression-of]] — ZipCCL: Efficient Lossless Data Compression of — ZipCCL (Lin, Pan, Fan, Shi, Chu; arXiv 2604.27844) is a lossless compression layer for NCCL collectives in LLM training. Core observation: LLM training tensors (activations, gradients, parameters) are near-Gaussian, so BF16 exponents are highly concentrated - the top-7 most frequent exponents cover >97% of the data. ZipCCL encodes each BF16 exponent in 3 bits (7 codes plus a zero-point escape flag) instead of 8, leaving sign/mantissa untouched, for a theoretical compression ratio up to 11 bits from 16 (~1.45x). It adds GPU-optimised compress/decompress kernels with communication-aware data layout and an adaptive switcher driven by a cost model over measured bandwidth, latency and compression ratio.

Evaluation: 64-GPU cluster of 8x RTX A6000 per node over a 200 Gb/s network, integrated into Megatron-LM (MoE all-to-all) and TorchTitan (FSDP all-gather/reduce-scatter), plus a 16xH800 400 Gb/s cluster. Communication speedups over NCCL: 1.25x on DeepSeek-V3 all-to-all, 1.24x on Qwen3-MoE, 1.35x on Llama3-8B all-gather; averaged across message sizes 1.36x for all-to-all and 1.31x for all-gather. End-to-end training speedups: 1.16x (DeepSeek-V3), 1.16x (Qwen3-MoE), 1.18x (Llama3-8B); on the 16xH800 cluster 1.13x for both Qwen3-MoE and Llama3-8B.

Two findings are load-bearing for this box. First, the benefit is bandwidth-saturation dependent: "When the data volume is small, bandwidth cannot be fully utilized, and our ZipCCL shows very close performance to NCCL. However, as the data volume increases ... and bandwidth is better saturated, the improvement ... becomes significant." On a ~1 GB/s fabric the saturation point arrives at far smaller tensors, so 1.3x is a floor rather than a ceiling. Second, Reduce-Scatter was NOT worth compressing on their platform ("the original Reduce-Scatter implementation was found to be faster"), so a DDP/FSDP gradient path does not automatically inherit the gain - all-gather did, reduce-scatter did not.

Also notable: ZipCCL beats DietGPU (Meta's GPU lossless compressor), where DietGPU-compressed all-gather was slower than plain NCCL all-gather while ZipCCL got 1.35x. The scheme is bit-exact, so unlike FP8/quantisation work it carries no convergence risk; the relevant risk on this box is compress/decompress kernel cost against 5 weak GPUs. `review`

- [[demystifying-nccl-an-in-depth-analysis-of-gpu]] — Demystifying NCCL: An In-depth Analysis of GPU — Demystifying NCCL (Hu, Shen et al., ETH Zurich + NVIDIA + Broadcom, arXiv 2507.04786, HOTI 2025): the primary reference for what NCCL actually does on a given fabric, and the mechanism behind the box's measured ~0.75 GiB/s all-reduce. Three protocol variants: Simple (near-peak bandwidth for large messages, ~6 us per-hop latency, memory fences), LL (4 B data + 4 B flag per 8-byte atomic, ~1 us per-hop, but only 25-50% of peak bandwidth because LL FORCES the intermediate buffer into host memory so the CPU can poll the flag, which precludes GPUDirect RDMA), and LL128 (120 B data + 8 B flag, ~95% of peak, ~2 us per-hop, but requires atomic 128-byte writes that are not split or reordered — NCCL disables LL128 on PCIe where that guarantee is absent). Intra-node transports are P2P (p2p.cc, GPUDirect P2P over NVLink or PCIe), SHM (shm.cc, host-staged), and NVLS; NCCL falls back to SHM not only when P2P is unavailable but also when P2P is suboptimal, e.g. inter-socket PCIe P2P. Algorithmically, Ring AllReduce executes 2k-1 steps per loop iteration and is NON-pipelined (each GPU must finish every task in one iteration before starting the next), so it is latency-bound on host-staged links; Tree AllReduce is pipelined but builds its branching structure only across nodes and links the GPUs inside a node in a simple chain, so on a single-node 5-GPU box the tree degenerates to a chain and buys nothing over ring. `review`
- [[efficient-multi-path-nvlinkpcie-aware-ucx-based-collective-communication-for-dee]] — Efficient Multi-Path NVLink/PCIe-Aware UCX based Collective Communication for Deep Learning — Temucin, Sojoodi, Alizadeh & Afsahi (HOTI 2021, Queen's University) show that a single NVLink/PCIe path badly under-utilises intra-node GPU-GPU bandwidth, and fix it with a multi-path copy that stripes messages across multiple NVLink channels, memory regions and GPU streams. On UCX this yields 1.69x higher bandwidth (72 -> ~122 GB/s) and 1.84x on Open MPI + UCX (up to 134 GB/s), on a 4xV100 POWER9 node with three intra-socket NVLinks.

They then build a 3-stage hierarchical, pipelined MPI_Allreduce: multi-path NVLink for intra-socket stages 1 and 3, and PCIe / X-Bus channels for the inter-socket stage 2, chosen per message size to minimise interference (PCIe Gen4 and X-Bus are both ~32 GB/s, so the X-Bus is the bottleneck on the NVLink-X-Bus-NVLink path). For 512 KB-1 GB messages the hierarchical allreduce beats Spectrum MPI, Open MPI+UCX, Open MPI+HPC-X, MVAPICH2-GDR and NCCL by up to 12.25x, 15.63x, 3.72x, 1.48x and 1.38x respectively; at 64 MB specifically the speedups are 11.47x, 14.33x, 1.09x, 1.26x and 1.25x. It outperforms NCCL for all messages >8 MB.

At the application layer with Horovod+TensorFlow: VGG16 gets up to 2.98x/3.42x/3.22x/1.23x/3.24x over those five libraries, ResNet50 1.50x/1.57x/1.22x/1.24x/1.23x.

Why it matters here: it establishes that NCCL is not a hard ceiling on a PCIe/NVLink intra-node fabric - a hierarchical collective that uses ALL available paths (including the host X-bus staging path a no-P2P box is forced onto anyway) can beat it by ~1.25x at >=8 MB. The mechanism is dated (2021, V100, NCCL 2.5.6) but the structural insight - one path at a time wastes bandwidth - is exactly the situation on a 5-GPU box with no P2P, where every collective round-trips through host RAM. `review`
- [[environment-variables-nccl-2323-documentation]] — Environment Variables — NCCL 2.32.3 documentation — NVIDIA's official NCCL 2.32.3 environment-variable reference - the primary source behind the tuning claims in the ClusterBid blog. Load-bearing entries for a no-P2P PCIe box:

NCCL_P2P_DISABLE disables the peer-to-peer transport ("CUDA direct access between GPUs, using NVLink or PCI"). NCCL_P2P_LEVEL sets the maximum topological distance at which P2P is used, with named levels LOC (never), NVL (NVLink), PIX (same PCI switch), PXB (through PCI switches, possibly multiple hops), PHB (same NUMA node, traffic through the CPU) and SYS (across NUMA nodes, potentially crossing QPI/UPI). Integer legacy values 0-4 map to LOC/PIX/PXB/PHB/SYS; NVL has no legacy integer.

NCCL_SHM_DISABLE documents the fallback path that matters most here: "SHM is used between devices when peer-to-peer cannot happen, therefore, host memory is used." That is the primary confirmation that a no-P2P box stages every collective through host RAM, and it names the knob (NCCL_SHM_DISABLE) that would force the network path instead.

NCCL_ALGO accepts Ring, Tree, Collnet, CollnetChain, CollnetDirect, NVLS, NVLSTree and PAT (2.23+), with per-function selection syntax since 2.24 and caret-prefixed exclusion lists. Default is unset, i.e. NCCL picks automatically from node topology and architecture. NCCL_PROTO accepts LL, LL128 and Simple; the docs warn users are "discouraged from setting this variable" and that "enabling LL128 on platforms that don't support it can lead to data corruption" - a direct caution against blindly copying tuning recipes.

Other relevant knobs: NCCL_BUFFSIZE, NCCL_NTHREADS, NCCL_MIN_NCHANNELS / NCCL_MAX_NCHANNELS (channel count trades CUDA blocks for bandwidth), NCCL_NVB_DISABLE (intra-node NVLink via an intermediate GPU), NCCL_PXN_DISABLE, NCCL_NET_GDR_LEVEL, and NCCL_IB_* for RDMA fabrics. Notably the docs do not support the blog's claim that NCCL_ALGO=Ring with NCCL_PROTO=LL is a recommended setting for >256-GPU clusters; that is vendor-blog folklore, not documented guidance. `review`
- [[github-mcrltccl-thunder-research-groups-collective-communication-library-github]] — GitHub - mcrl/tccl: Thunder Research Group's Collective Communication Library · GitHub — TCCL (Thunder Research Group, SNU; ASPLOS 2024; github.com/mcrl/tccl): a fork of NCCL for 'PCIe-dependent systems' — clusters where GPUs must communicate through the CPU's PCIe host bridge and possibly NUMA interconnects, with no NVLink and no external PCIe switches. Its premise is the key claim for this run: existing collective libraries do NOT achieve the performance their analytical models predict on PCIe-dependent systems, for two reasons that only appear when traffic goes through the CPU — transfers slow down when multiple transfers traverse the CPU in a particular pattern because of NUMA architecture, and bounce buffers are poorly placed when GPUs communicate via CPU memory. Neither congestion pattern shows up on links that bypass the CPU, so NCCL's topology logic never learns to avoid them. TCCL's pathfinder profiles each candidate communication path and merges single-node paths into multi-node paths (brute force is exponential in GPU count), and the runtime is a drop-in libnccl.so replacement selected via NCCL_ALGO=TCCL plus TCCL_XML_FILE. Thin source (README only, ~1.1k words) but ground-truth tier: it is the code artifact behind the ASPLOS paper, last committed Jul 2025. `review`

- [[cramming-training-a-language-model-on-a]] — CRAMMING: TRAINING A LANGUAGE MODEL ON A — Cramming (Geiping & Goldstein, arXiv 2212.14034) is the canonical single-GPU compute-budget study: train a transformer LM from scratch with masked LM on one GPU for 24 hours and measure GLUE. Hardware tested: RTX 2080 Ti (11 GB), RTX A4000 (16 GB), RTX A6000 (48 GB), each paired with 4 CPU cores and 32 GB RAM; the A6000 run reaches BERT-base-class GLUE in one day.

Findings that bear on CMP 170HX feasibility: (1) scaling laws hold in the extreme low-compute regime — per-token training efficiency depends strongly on model size but not on transformer type, so architecture changes only help insofar as they raise throughput at constant parameter count; (2) the authors explicitly find no benefit from CPU/NVMe offloading in this setting; (3) FlashAttention (Dao et al. 2022) is only re-enabled for the final architecture variant after ablations, i.e. it is a throughput lever, not an accuracy lever; (4) the ablation accounting attributes ~2 GLUE points to architecture changes, ~1 point to data changes, and ~0.5 point to training-recipe changes; (5) sequence length 128 with packed sequences gives micro-batches of 64-96 on the 2080 Ti, accumulated into larger batches, and single-epoch training is feasible at this budget.

Relevance: it is the strongest published evidence that a single GPU with no interconnect at all can produce a usable model in a bounded wall-clock budget — the limiting case of the CMP 170HX box (5 cards, no NVLink, no P2P). It also warns that offloading, a plausible workaround for a 64 GB-per-card memory ceiling, bought nothing in their measurements. `review`
- [[efficient-training-on-multiple-consumer-gpus-with]] — Efficient Training on Multiple Consumer GPUs with — RoundPipe (Luo et al., Tsinghua, SIGOPS ATC 2026, arXiv 2604.27085): pipeline parallelism + CPU offloading for LLM fine-tuning on consumer GPUs. Directly relevant to the CMP 170HX topology question because RoundPipe uses NO GPU peer-to-peer communication at all — it relies entirely on PCIe host-to-device transfers under its Computation Dispatch Paradigm, and still reaches 1.48-2.16x the throughput of the fastest baselines (ZeRO-2, FSDP, ZeRO-Infinity, Megatron-PP, Megatron-TP, Mobius) on 8x RTX 4090 (PCIe 4.0, 32 GB/s) for 1.7B-32B models, and 76%+ of the same frameworks on 8x A800. It quantifies the DDP/ZeRO penalty on this class of fabric: DeepSpeed spends ~70% of training time on communication on consumer GPU servers, and Megatron-TP's throughput 'becomes impractical under PCIe'. Memory anchors: an 8B model needs 128 GB for model states alone (vs 24 GB per 4090), host memory footprint is ~20x parameter size, activation recomputation is 2.37-5.75x faster than reloading activations over PCIe, and max trainable sequence length is independent of GPU count (73K/49K/39K/28K/31K for the five models) because stage-boundary activations live in host DRAM. Bubble ratio falls below 4.5% with asynchronous optimizer updates; near-linear scaling from 1 to 8 GPUs; LoRA fine-tunes Qwen3-235B at 31K sequence length on 24 GB cards. `review`
- [[llmq-efficient-lower-precision-pretraining]] — LLMQ: Efficient Lower-Precision Pretraining — LLMQ (Schultheis & Alistarh, IST Austria, arXiv 2512.15306, Dec 2025; CPAL 2026): an end-to-end CUDA/C++ training framework for 3B-32B models on commodity GPUs, and the strongest primary evidence that the memory half of this box's problem is solvable. It trains or fine-tunes a 7B model on a SINGLE 16 GB card (RTX 5060Ti, 70% MFU) via 8-bit training, selective recomputation, optimizer-state offload and chunked logits/attention workspace, and a 32B model on 4x RTX 4090 at 3,400 tok/s / 51% MFU (vs 29% MFU on 4x L40S); 14B on the same 4x4090 runs at 7,800 tok/s / 54% MFU, and a single 4090 trains up to 14B. Two findings bear directly on the topology question. First, on recent consumer GPUs the cards cannot communicate directly over PCIe, so placing weights in host memory actually REDUCES required communication: weights go GPU->host once after each optimizer step and are then reused from the host cache across the backward pass and all gradient-accumulation forwards; consequently LLMQ enables sharded weights BEFORE sharded gradients, the reverse of classic ZeRO ordering. Second, NCCL all-gather/reduce-scatter on PCIe showed 'quite low' link utilization, while cudaMemcpy transfers driven by the GPU copy engines achieve much better utilization and reserve no SMs for communication kernels; LLMQ implements all-gather and a three-phase memcpy-based reduce-scatter on copy engines, overlapped with the backward pass of the next transformer block. Table 4 anchors the hardware gap: H100 vs RTX 4090 is 989.4 vs 165.2 BF16 TFLOP/s (6x), 80 vs 24 GB, 900 GB/s NVLink vs 64 GB/s PCIe 4.0 (14x). `review`

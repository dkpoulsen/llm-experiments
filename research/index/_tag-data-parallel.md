- [[mics-near-linear-scaling-for-training-gigantic-model-on-public]] — MiCS: Near-linear Scaling for Training Gigantic Model on Public — MiCS (JHU / AWS / Peking University): minimizes communication scale - the number of participants in each collective - rather than communication volume, so that collectives stay inside the fastest available group. The motivating asymmetry: DGX-2/DGX-A100 clusters have intra-node bandwidth only about 3x faster than inter-node, so ZeRO's flat all-device partitioning is tolerable; public-cloud V100 instances on 100 Gbps networks have intra-node bandwidth about 24x faster than inter-node, so flat partitioning is not. MiCS adds scale-aware model partitioning and a hierarchical communication strategy. Results on AWS: 2.89x throughput over DeepSpeed on V100/100 Gbps, up to 2.74x on A100-40GB/400 Gbps, 30.1% better than Megatron-LM-3D, 99.4% weak-scaling efficiency, and a 100B model at over 170 TFLOPS per A100 across 512 GPUs. Directly relevant because a 5-GPU PCIe box has no fast tier at all, so 'minimize scale' collapses to 'use all five cards in one flat group'. `review`
- [[pytorch-fsdp-experiences-on-scaling-fully-sharded-data-parallel-pvldb-16]] — PyTorch FSDP: Experiences on Scaling Fully Sharded Data Parallel (PVLDB 16) — Meta's canonical PyTorch FSDP paper (PVLDB 16(12):3848-3860, 2023; open-access copy of doi 10.14778/3611540.3611569). States explicitly that full sharding 'has 1.5x communication overhead and volume over DDP if using bandwidth optimal ring algorithm' - the primary source for the 1.5x FSDP-vs-DDP multiplier. DDP needs parameters, gradients and optimizer states resident on one device: 'when training models with more than one billion parameters using a 40GB GPU device, DDP will likely encounter out-of-memory errors on each device.' Measured on A100-80GB over 2Tb/s RoCE: FSDP matches DDP at 611M (15.18 vs 14.61 TFLOPS/GPU) and 2.28B (27.40 vs 25.76), then DDP OOMs while FSDP trains 11.3B at 148.48 TFLOPS/GPU in BF16; backward prefetch gives ~18% speedup on GPT-175B; 175B reaches 173-186 TFLOPS/GPU against a 312 TFLOPS BF16 peak. Sharding factor F: F=1 degenerates to DDP AllReduce, F=W is full sharding, 1<F<W is hybrid sharding that keeps shard groups inside a node to exploit higher intra-node bandwidth; TP+FSDP 2D mesh keeps TP intra-node and FSDP inter-node. Mixed precision lets all collectives run in low precision, cutting comm volume. Caveats: optimizer math on FlatParameters breaks mathematical equivalence for norm-dependent optimizers; shared parameters must live in the lowest-common-ancestor FSDP unit. `review`
- [[zero-memory-optimizations-toward-training-trillion-parameter-models-sc20]] — ZeRO: Memory Optimizations Toward Training Trillion Parameter Models (SC20) — ZeRO (SC20) canonical memory-optimization paper, arXiv copy of doi 10.1109/sc41405.2020.00024. Derives the DP communication-volume arithmetic this run needs: an all-reduce is reduce-scatter plus all-gather, each moving Psi elements, so standard DP costs 2Psi per step; ZeRO-1/2 (Pos+g) stays at exactly 2Psi; ZeRO-3 (Pos+g+p) costs 3Psi, i.e. 1.5x baseline DP. Memory: a 7.5B model needs 120 GB under standard DP, 31.4 GB (Pos, Nd=64), 16.6 GB (Pos+g), 1.88 GB (Pos+g+p); 'Without ZeRO, the largest model DP alone can run has less than 1.5 Billion parameters' on 32 GB V100s; 1T parameters fit on 1024 GPUs. Empirically on 400 V100s (25 DGX-2 nodes, 800 Gbps inter-node): 170B model, 15 PFLOPs sustained (>30% of peak), 38 TFLOPS/GPU on 60B, 8x model size and 10x performance over Megatron-LM. Explicitly rejects CPU offload because PCIe bandwidth is 'severely constrained' - up to 50% of training time can go to GPU-CPU-GPU transfers. Notes that crossing a node boundary drops per-link bandwidth from 300 GB/s (NVSwitch) to 12.5 GB/s (InfiniBand EDR). `review`

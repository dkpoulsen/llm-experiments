- [[demystifying-nccl-an-in-depth-analysis-of-gpu]] — Demystifying NCCL: An In-depth Analysis of GPU — Demystifying NCCL (Hu, Shen et al., ETH Zurich + NVIDIA + Broadcom, arXiv 2507.04786, HOTI 2025): the primary reference for what NCCL actually does on a given fabric, and the mechanism behind the box's measured ~0.75 GiB/s all-reduce. Three protocol variants: Simple (near-peak bandwidth for large messages, ~6 us per-hop latency, memory fences), LL (4 B data + 4 B flag per 8-byte atomic, ~1 us per-hop, but only 25-50% of peak bandwidth because LL FORCES the intermediate buffer into host memory so the CPU can poll the flag, which precludes GPUDirect RDMA), and LL128 (120 B data + 8 B flag, ~95% of peak, ~2 us per-hop, but requires atomic 128-byte writes that are not split or reordered — NCCL disables LL128 on PCIe where that guarantee is absent). Intra-node transports are P2P (p2p.cc, GPUDirect P2P over NVLink or PCIe), SHM (shm.cc, host-staged), and NVLS; NCCL falls back to SHM not only when P2P is unavailable but also when P2P is suboptimal, e.g. inter-socket PCIe P2P. Algorithmically, Ring AllReduce executes 2k-1 steps per loop iteration and is NON-pipelined (each GPU must finish every task in one iteration before starting the next), so it is latency-bound on host-staged links; Tree AllReduce is pipelined but builds its branching structure only across nodes and links the GPUs inside a node in a simple chain, so on a single-node 5-GPU box the tree degenerates to a chain and buys nothing over ring. `review`

They then build a 3-stage hierarchical, pipelined MPI_Allreduce: multi-path NVLink for intra-socket stages 1 and 3, and PCIe / X-Bus channels for the inter-socket stage 2, chosen per message size to minimise interference (PCIe Gen4 and X-Bus are both ~32 GB/s, so the X-Bus is the bottleneck on the NVLink-X-Bus-NVLink path). NCCL_P2P_DISABLE disables the peer-to-peer transport ("CUDA direct access between GPUs, using NVLink or PCI"). NCCL_P2P_LEVEL sets the maximum topological distance at which P2P is used, with named levels LOC (never), NVL (NVLink), PIX (same PCI switch), PXB (through PCI switches, possibly multiple hops), PHB (same NUMA node, traffic through the CPU) and SYS (across NUMA nodes, potentially crossing QPI/UPI). Integer legacy values 0-4 map to LOC/PIX/PXB/PHB/SYS; NVL has no legacy integer.

NCCL_SHM_DISABLE documents the fallback path that matters most here: "SHM is used between devices when peer-to-peer cannot happen, therefore, host memory is used." That is the primary confirmation that a no-P2P box stages every collective through host RAM, and it names the knob (NCCL_SHM_DISABLE) that would force the network path instead.

NCCL_ALGO accepts Ring, Tree, Collnet, CollnetChain, CollnetDirect, NVLS, NVLSTree and PAT (2.23+), with per-function selection syntax since 2.24 and caret-prefixed exclusion lists. Default is unset, i.e. NCCL picks automatically from node topology and architecture. NCCL_PROTO accepts LL, LL128 and Simple; the docs warn users are "discouraged from setting this variable" and that "enabling LL128 on platforms that don't support it can lead to data corruption" - a direct caution against blindly copying tuning recipes.

Other relevant knobs: NCCL_BUFFSIZE, NCCL_NTHREADS, NCCL_MIN_NCHANNELS / NCCL_MAX_NCHANNELS (channel count trades CUDA blocks for bandwidth), NCCL_NVB_DISABLE (intra-node NVLink via an intermediate GPU), NCCL_PXN_DISABLE, NCCL_NET_GDR_LEVEL, and NCCL_IB_* for RDMA fabrics. Notably the docs do not support the blog's claim that NCCL_ALGO=Ring with NCCL_PROTO=LL is a recommended setting for >256-GPU clusters; that is vendor-blog folklore, not documented guidance. `review`
- [[evaluating-modern-gpu-interconnect-pcie]] — Evaluating Modern GPU Interconnect: PCIe, — Li, Song, Chen, Li, Liu, Tallent & Barker (PNNL; arXiv 1903.04611, IEEE TPDS) is the canonical primary evaluation of modern GPU interconnects - PCIe, NVLink-V1, NVLink-V2, NV-SLI, NVSwitch and GPUDirect-RDMA - across six platforms: P100-DGX-1, V100-DGX-1, DGX-2, OLCF SummitDev, Summit, and a 2x Turing RTX-2080 SLI system. They measure raw startup latency, sustainable uni/bidirectional bandwidth, topology, routing and NUMA effects under both P2P and collective (NCCL) patterns.

Four new NUMA effects are identified: three triggered by NVLink topology/connectivity/routing, and one by a PCIe chipset design issue they label "anti-locality" - nearby access presenting LOWER performance than remote access, observed only for bandwidth (not latency) and appearing for messages >64 KB. PCIe latency is essentially uniform across pairs (same through one PCIe switch, across a local CPU socket, or across the QPI bridge), i.e. no NUMA effect in PCIe latency; NVLink latency is ~9 us direct and rises ~2x (P100) / ~3x (V100) when routing is required. NV-SLI: local 5 us, NV-SLI 8 us, PCIe 13 us. NVSwitch gives 50 GB/s bidirectional per link, 300 GB/s via a single NVSwitch hop, and 2.4 TB/s baseboard-to-baseboard bisection.

Message-size saturation points differ by an order of magnitude: NCCL collective bandwidth saturates at ~16 MB on PCIe but ~256 MB on NVLink (8 GPUs); on a 2-GPU SLI system both PCIe and NV-SLI saturate at ~1 MB.

THE finding for this run: "the NUMA effects appear quite significant with 5 GPUs, implying that there may be a congestion when forming a NCCL ring among 5 GPUs. One should avoid adopting 5 GPUs in their application setup." The box under assessment has exactly 5 GPUs, so this is a direct, primary-sourced warning that a 5-rank NCCL ring is a pathological configuration on PCIe.

Their discussion adds two structural cautions: NVLink's advantage is bandwidth, not latency, over PCIe; and a faster interconnect alone "can hardly become significant enough to lift the entire application's speedup" unless the CPU-centric master-slave programming model is replaced or communication control moves to the GPU (e.g. NVSHMEM). NVLink also introduces its own overheads (enable/disable peer access, routing, NCCL initialization). `review`

- [[zipccl-efficient-lossless-data-compression-of]] — ZipCCL: Efficient Lossless Data Compression of — ZipCCL (Lin, Pan, Fan, Shi, Chu; arXiv 2604.27844) is a lossless compression layer for NCCL collectives in LLM training. Core observation: LLM training tensors (activations, gradients, parameters) are near-Gaussian, so BF16 exponents are highly concentrated - the top-7 most frequent exponents cover >97% of the data. ZipCCL encodes each BF16 exponent in 3 bits (7 codes plus a zero-point escape flag) instead of 8, leaving sign/mantissa untouched, for a theoretical compression ratio up to 11 bits from 16 (~1.45x). It adds GPU-optimised compress/decompress kernels with communication-aware data layout and an adaptive switcher driven by a cost model over measured bandwidth, latency and compression ratio.

Evaluation: 64-GPU cluster of 8x RTX A6000 per node over a 200 Gb/s network, integrated into Megatron-LM (MoE all-to-all) and TorchTitan (FSDP all-gather/reduce-scatter), plus a 16xH800 400 Gb/s cluster. Communication speedups over NCCL: 1.25x on DeepSeek-V3 all-to-all, 1.24x on Qwen3-MoE, 1.35x on Llama3-8B all-gather; averaged across message sizes 1.36x for all-to-all and 1.31x for all-gather. End-to-end training speedups: 1.16x (DeepSeek-V3), 1.16x (Qwen3-MoE), 1.18x (Llama3-8B); on the 16xH800 cluster 1.13x for both Qwen3-MoE and Llama3-8B.

Two findings are load-bearing for this box. First, the benefit is bandwidth-saturation dependent: "When the data volume is small, bandwidth cannot be fully utilized, and our ZipCCL shows very close performance to NCCL. However, as the data volume increases ... and bandwidth is better saturated, the improvement ... becomes significant." On a ~1 GB/s fabric the saturation point arrives at far smaller tensors, so 1.3x is a floor rather than a ceiling. Second, Reduce-Scatter was NOT worth compressing on their platform ("the original Reduce-Scatter implementation was found to be faster"), so a DDP/FSDP gradient path does not automatically inherit the gain - all-gather did, reduce-scatter did not.

Also notable: ZipCCL beats DietGPU (Meta's GPU lossless compressor), where DietGPU-compressed all-gather was slower than plain NCCL all-gather while ZipCCL got 1.35x.
